PART 2 — ANALYSIS AND RISK REGISTER 2.1 What the design gets right (validated by research and two adversarial reviews) Four	foundational	instincts	survived	verification	and	red-teaming	and	are	preserved	verbatim	in	intent:	a)	Classification	before	action.	Every	input	is	analyzed	for	domain,	entity,	and	category	before	anything	is	done	with	it.	One	taxonomy,	one	rule	set,	one	place	to	improve	accuracy	—	the	architectural	spine.	b)	Person-	and	entity-level	segregation.	Personal	life	split	by	person,	business	by	legal	entity,	maps	to	real	boundaries:	separate	returns,	accounts,	liability,	and	retention	obligations.	Building	the	entity	dimension	in	from	day	one	avoids	an	expensive	re-file	later.	c)	Learning	from	prior	behavior,	human-gated.	Deriving	the	voice	profile	from	sent	mail	and	calendar	conventions	from	history	—	rather	than	asking	the	owner	to	describe	them	—	is	the	correct	approach,	and	the	corrections→proposed-rule→owner-approval	loop	is	the	published	"evolving	playbook"	pattern	with	a	human	curator,	which	the	memory-governance	literature	identifies	as	the	defensible	variant	for	regulated	data.	No	shipping	email	product	does	even	this	much.	d)	The	security	control	sits	in	architecture,	not	model	trust.	The	tool-less	airlock,	the	four	permanent	hard	stops,	and	local-first	inference	are	the	right	controls	precisely	because	no	model	—	including	frontier	models	with	vendor	safeguards	—	resists	prompt	injection	well	enough	to	be	trusted	architecturally	(best	measured	resistance	is	meaningfully	above	zero	even	with	safeguards).	2.2 What v3.0 fixes relative to v2.0 The	two	adversarial	reviews	of	v2.0	found	the	architecture	sound	but	the	document	and	its	commercial	framing	weak.	v3.0's	material	fixes:	1. Self-containment	(Rec	1).	No	content	is	incorporated	by	reference;	this	is	the	sole	governing	document.	2. The	one	real	security	contradiction	(Rec	3).	v2.0's	trifecta	ledger	claimed	the	drafting	agent	had	"no	egress"	while	granting	it	automatic	cloud	escalation.	v3.0	makes	cloud	escalation	on	client-facing	drafts	owner-initiated	only,	restoring	the	invariant	that	no	autonomous	flow	combines	private	data,	untrusted	content,	and	egress.	3. The	commercial	layer	(Recs	6–11).	v2.0	called	itself	"contract-grade"	while	containing	no	price,	payment	structure,	IP	terms,	warranty,	developer	data-handling	obligations,	offboarding,	or	support	retainer.	Part	12	supplies	the	framework;	counsel	papers	it.	4. Owner	protection	in	measurement	(Rec	10).	The	developer	no	longer	grades	his	own	exam:	a	sealed	holdout	set,	owner-approved	labels,	a	named	institution	schedule,	and	metric	audit	rights	are	now	contractual.	5. Adoption	design	(Recs	12,	35).	Graduated	per-class	shadow	mode	replaces	a	per-phase	autonomy	switch;	a	thin	read-only	digest	ships	in	Phase	4	so	value	is	visible	in	week	~5;	backfill	runs	after	trust	is	established.	6. Year-2	survivability	(Recs	19–24).	RTO/RPO	targets,	a	LaunchDaemon	that	persists	the	GPU	wired-memory	limit	across	reboots,	timezone-safe	scheduling,	an	idempotent	durable	queue,	a	platform	exit	strategy,	and	a	compliance	calendar	with	execution	owners	—	the	difference	between	a	system	that	runs	for	three	months	and	one	that	runs	for	three	years.	7. PART 4 — TARGET ARCHITECTURE 4.1 Design principles 1. One	classifier,	many	inputs.	Every	input	converges	on	the	same	classification	contract	(§14.1).	A	new	channel	is	a	new	adapter,	never	a	new	taxonomy.	2. Local-first	inference.	The	Mac	Studio	is	primary	compute;	cloud	is	a	logged	exception.	Tax-engagement	and	privileged	artifacts	never	reach	cloud	at	all	(DEC-3,	DEC-10).	3. Separation	of	reading	from	acting	—	extended	to	storage.	The	agent	that	reads	untrusted	content	has	no	consequential	tools.	The	agent	that	acts	never	receives	untrusted	strings	—	not	raw	text,	and	not	laundered	through	validated	JSON.	Every	stored	string	derived	from	external	content	carries	a	permanent	untrusted	taint	and	is	re-wrapped	in	boundary	markers	on	any	later	read	into	a	model	context.	4. Deterministic	filing,	probabilistic	classification.	Models	decide	what	it	is;	code	decides	where	it	goes.	5. Every	action	reversible	or	logged;	every	pipeline	stage	idempotent.	Nothing	happens	that	cannot	be	traced	to	an	input,	a	classification,	a	rule	version,	and	a	timestamp	—	and	re-processing	the	same	input	never	double-acts	(§7.1.6).	6. Skills	over	code	—	but	zero	third-party	skills.	All	SKILL.md	files	are	hand-authored	in-repo	and	version-pinned.	ClawHub	installs	are	prohibited.	7. Fail	loud.	Heartbeats,	watchdogs,	production	canaries,	and	a	daily	"here	is	what	I	did"	digest	are	mandatory.	8. Enforce	below	the	agent.	Egress	allowlists	live	in	the	OS	firewall,	secrets	in	the	Keychain,	version	pinning	in	the	update	channel,	and	the	GPU	memory	limit	in	a	boot-persistent	daemon	—	places	an	injected	model	cannot	reach.	9. Autonomy	is	earned,	not	switched	on. PART 7 — PROCESSING PIPELINES 7.1 The universal pipeline Every	input,	regardless	of	channel,	traverses	the	same	nine	stages.	Stages	1–4	are	mandatory;	5–9	are	conditional	on	classification.	1. CAPTURE    → adapter normalizes to an Artifact record + raw bytes in staging	2. SANITIZE   → wrap in <<EXTERNAL_UNTRUSTED_CONTENT>> markers; strip active content;	                sanitize contact/display-name and vCard fields; scan attachments;	                quarantine encrypted/unparseable	3. EXTRACT    → TIER-0 deterministic parse first; TIER-OCR vision/OCR if needed;	                TIER-A transcription for audio	4. CLASSIFY   → ingest-sandbox agent (zero tools) emits the classification JSON under	                json_schema constrained decoding; ≤2,500-token prompt (taxonomy skeleton	                + retrieved rule subset only)	5. DEDUPE     → three-stage check (§6.4)	6. FILE       → deterministic path computed by code; write; sidecars; hash recorded	7. RECORD     → ledger/task/event/matter/renewal rows as applicable	8. ACT        → autonomy matrix (Part 8) decides: execute (if graduated) / draft / gate / notify	9. High-stakes	actions	require	harder	evidence:	• Ledger	writes	require	two-pass	agreement,	and	decorrelation	is	defined	so	the	gate	is	not	vacuous:	pass	1	runs	the	standard	prompt	at	temperature	0;	pass	2	runs	a	paraphrased	prompt	at	temperature	0.4	(or	a	different	quantization	of	L1).
